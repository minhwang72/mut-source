- 붙임줄·붙임점·속 빈 머리·쉼표 오검출은 남아 있다. 출력 차단은 인식 정확도가 좋아졌다는 뜻이 아니다.

## XML 재조판 완성 (2026-09-01) — 무엇이 실제 원인이었나

### 증상

마커스 악보의 속 빈 머리(2분·온음표) 15개 중 **1개만** 검출됐다. 오분류가
아니라 아예 안 잡혔다. 그 15개는 음높이가 비어 재조판된 멜로디가 틀렸다.

### 가설 1 — "학습 데이터에서 구멍이 메워진다" (부분적으로 맞음)

단계별로 분리해 실측했다 (합성 105개 표본, 구멍 생존율):

| 열화 | 생존율 |
|---|---|
| 원본 그대로 | 80% ← 측정기 자체 상한 |
| 축소만 (6.5~12px) | 76~80% |
| JPEG 품질 50 | 81% |
| 블러 0.7 | 47% |
| **MinFilter(3) — 잉크 부풀리기** | **7%** |

**부풀리기가 범인이었다.** "축소 전에 부풀리면 된다"는 이전 가설은 틀렸다 —
확대→침식→축소로 부분 픽셀만 번지게 해도 23~42%였다. 머리 높이 8px에서
구멍은 원래 2px이라 어떤 침식도 메운다.

그래서 **구멍을 살리는 대신 라벨을 그림에 맞췄다** (`gendata.relabel_hollow`):
열화 뒤 상자마다 구멍을 재보고 사라졌으면 `notehead_filled`로 정정한다.
표본을 버리지 않고 부류만 옮긴다.

```
흰 머리 라벨의 정직도   50%  →  100%
정직한 흰 머리 표본   6,100  →  17,353개
```

곁가지로 두 버그도 나왔다:
- `staffLineWidth 0.335`가 Verovio 상한(0.300)을 넘어 **조용히 기본값으로
  되돌아갔다** — 선 굵기 다양화가 절반만 작동했다.
- 온음표 표본이 956개(꽉찬 머리의 1/163)였다. 온음표는 마디를 혼자 채우니
  머리 1개, 8분음표는 8개가 나온다. 실제 분포를 그대로 쓰면 표본이 안 모인다.

### 가설 2 — "합성과 실제의 모양이 다르다" (틀림)

폰트 5종과 실제 악보를 실측했더니 **겹쳤다**:

| | 폭/높이 | 구멍 면적비 | 머리높이/오선간격 |
|---|---|---|---|
| 실제 (마커스) | 1.17 | 38% | 1.23 |
| 합성 (5폰트) | 1.00~1.30 | 35~46% | 0.99~1.30 |

눈으로 본 "실제는 둥글고 뚱뚱하다"는 인상은 **확대 배율이 달라서** 생긴
착시였다. 그리고 이 측정 자체도 한 번 틀렸다 — 처음엔 오선 밖까지 훑어
부제 글자("My heart sings praises")를 머리로 셌다.

### 가설 3 — "추론 경로가 다르다" (틀림)

| 경로 | 머리 | 흰 |
|---|---|---|
| 단별 정규화 6.5px | 116 | 1 |
| 쪽 전체 imgsz 960 | 117 | 2 |
| 쪽 전체 imgsz 1280 | 115 | 0 |
| 2·3배 확대 | 115 | 0 |

어떤 경로든 0~2개였다.

### 실제 원인 — 신뢰도 분포가 부류마다 다르다

합성 검증셋과 실제 악보를 같은 모델로 비교한 것이 답을 줬다:

```
합성 검증셋 흰 머리 재현율  84%   (1에폭 모델)
실제 악보  흰 머리 재현율   7%
```

학습은 되고 있었다. 문턱을 낮춰 보니:

```
conf 0.50 → 흰 1개
conf 0.30 → 흰 5개
conf 0.15 → 흰 7개
conf 0.05 → 흰 11개
점수: 0.58 0.49 0.39 0.37 0.35 0.25 0.16 0.13 …
```

**모델은 보고 있었고 문턱에서 잘렸다.** 꽉 찬 머리는 0.9대에서 나오므로
하나의 문턱으로 둘을 같이 잡을 수 없다. 문턱을 그냥 낮추면 오검출이 는다.

### 해법 — 개수를 단서로 문턱을 정한다

**몇 개인지는 이미 안다.** LLM이 단별 음표 수를 읽어 준다. 그래서
높은 문턱으로 확실한 것부터 채우고, **개수가 모자라는 만큼만** 낮은 점수
후보를 겹치지 않게 더 받는다 (`evaldet.detect_guided`).

```
                      머리 (정답 132)   흰 머리 (정답 15)
옛 모델 · 문턱 0.50만      116               1   ( 7%)
옛 모델 · 개수 단서        126               3   (20%)
새 모델 · 문턱 0.50만      121               6   (40%)
새 모델 · 개수 단서        129              14   (93%)
```

**두 개선이 곱해진다.** 정직한 라벨로 재학습만 하면 40%, 개수 단서만 쓰면
20%인데, 둘을 합치면 **93%**다. 라벨이 정직해져 모델의 점수가 올라가고,
개수 단서가 그 올라간 점수를 받아들일 수 있게 되기 때문이다.

재조판 결과: 음높이 미확정 **15개 → 2~4개**.

이건 두 판독기를 **서로의 사전 정보로 쓰는** 구조다. CV는 위치를, LLM은
개수를 준다. 어느 쪽도 혼자서는 못 하는 일이다.

### 곁들여 잡은 것들

- **박자 검산** (`tools/checkbeats.py`) — 정답 악보가 없어도 4/4박이면 마디마다
  음가 합이 맞아야 한다. 쉼표까지 읽게 하니 39마디 중 **38개 확인**, 나머지
  1개를 "불확실"로 표시했다. 자동 오류 검출기다.
- **단 경계에서 쪼개진 마디** — 악보는 마디 중간에서 줄을 바꾼다. 앞 단
  마지막 마디(2박)와 뒷 단 첫 마디(2박)가 한 마디다. 모르면 **없는 줄막대를
  하나 그린다.** MusicXML은 마디 중간 줄바꿈을 못 쓰므로 두 조각으로 적고
  사이 줄막대를 `<bar-style>none</bar-style>`으로 지운다.
- **쉼표가 머리를 소비하는 버그** — 구조 읽기가 쉼표를 세게 된 뒤, 쉼표에
  음높이를 붙이면 그 뒤 음표가 한 칸씩 밀려 멜로디 전체가 어긋났다.
- **음이름 표가 F5~F3에서 끊김** — 오선 위 덧줄(G5·A5)이 `step-1`이 되어
  MusicXML이 깨졌다. 계산식으로 바꿨다(E6~C2 31개 값 파이썬·JS 일치 확인).
- **가사가 다음 단 코드와 겹침** — Verovio는 가사를 모르니 단 간격을 필요한
  값의 60%로 잡는다(실측: 111px vs 필요 180px). **원본의 비율을 재서** 페이지
  크기·배율·단 간격을 정한다(`renderpage.fit_to`).
- **cairosvg에서 코드의 ♭이 □** — 폰트가 SVG 안에 WOFF2 base64로 박혀 있는데
  cairosvg가 지원하지 않는다. **브라우저에서는 정상**이고, `<img>`→캔버스
  경로에서도 살아남는다(실측 확인).
- **구조 판독이 서버에서 실패** — 이미 2.8배 확대된 이미지를 또 6배 하니
  9,900px로 API 상한(8,000px)을 넘었다. 고정 배수 대신 **목표 오선 간격
  (39px)으로 배율을 계산**한다. 그리고 단 9개를 동시에 부르니 529 과부하가
  걸려 지수 대기 재시도를 넣었다(동시 4개).

### 코드 배치 — 마디당 하나로는 19%를 버린다

실측: 마커스 악보는 **코드 43개 · 마디 39개**다. 한 마디에 코드가 둘 이상인
경우가 흔해서, "마디당 하나"로 나눠 주면 **8개(19%)가 조용히 사라졌다.**

여기서도 가설을 세 번 틀렸다.

| 시도 | 결과 |
|---|---|
| 마디 중간에 `<harmony>` 끼워 넣기 | Verovio가 위치마다 세로 공간을 따로 잡아 코드가 오선 위 별도 띠로 밀려나고 서로 겹쳤다 |
| `<offset>`으로 가로 위치 주기 | 똑같았다. 단 간격이 156px → 193~377px로 널뛰었다 |
| 마디 폭을 균등하다고 보고 x로 나누기 | 원본은 음표 수에 따라 마디 폭을 늘린다 — 어긋났다 |

**진짜 원인:** Verovio는 한 마디에 `<harmony>`가 여러 개면 **세로로 쌓는다.**
가로 위치를 어떻게 주든 상관없다.

**해법 둘:**

1. **마디를 쪼개고 줄막대를 지운다.** 코드 자리에서 마디를 두 조각으로 나눠
   마디당 코드 하나로 만들고, 사이 줄막대를 `<bar-style>none</bar-style>`으로
   숨긴다. 보이는 그림은 한 마디 그대로다 — 단 경계에서 쪼개진 마디에 쓰던
   방법과 같다. 쉼표만 있는 마디는 **쉼표를 반으로 나눈다**(온쉼표 → 2분쉼표
   둘). 실측: 코드가 겹치는 마디 9개 → 3개 → **1개**.

2. **코드를 어느 마디에 놓을지는 막대선으로 정한다.** 음표에 직접 붙이면
   쉼표만 있는 마디의 코드가 갈 곳이 없어 다음 마디로 몰린다(실측: 마커스
   단0은 앞 4마디가 전부 쉼표라 코드 5개가 한 마디에 쌓였다).
   CV 막대선 검출은 저해상도에서 과검출하지만 — 오선 오른쪽 끝을 세고, 6px
   떨어진 중복을 따로 센다 — **LLM이 마디 수를 주므로 그 수에 맞춰 고를 수
   있다**(`layout.barlines_fit`). 음표 검출에서 개수를 단서로 문턱을 정한 것과
   같은 구조다. 실측: 9단 전부 정확.

**곁들여 잡은 좌표계 버그:** 코드 상자 x에 확대 배율을 곱했는데, 판독이 이미
확대본에서 이뤄져 **두 번 곱한 셈**이었다(x가 1392 → 3855가 되어 코드가 전부
마지막 마디로 밀렸다). 좌표계는 추측하지 말고 `extraction["imageSize"]`가
말하는 대로 쓴다.

결과: **코드 43/43개가 원본과 같은 자리에.** 단1이 `B♭ Gm7 F2 B♭ Cm7 F B♭`로
정확히 재현된다.

### 가사 오려내기 — 한글은 세로 획만 남는다

두 번째 악보(위싱 콘티)를 재조판했더니 가사가 **자모 조각**으로 나왔다:
"난"→"ㄴ", "에"→"ㅣㅣ", "하"→"히", "리"→"ㄹ".

여기서도 가설을 두 번 틀렸다.

| 가설 | 결과 |
|---|---|
| 2차 분할 간격이 너무 작다 | 맞았지만 원인이 아니었다. 폭 기준 분할로 바꿔도 그림은 그대로였다 |
| 음절 분할이 문제다 | 아니었다. 오려낸 조각 자체가 이미 반쪽이었다 |

**진짜 원인:** 열 판정 문턱이 `열 높이의 22%가 잉크`였다. 한글의 **가로 획은
한두 줄만 차지**하므로 세로 획만 켜지고, 오려낸 x구간이 5~8px이었다(실제 음절
폭 14px, 오선 간격 7px). 잉크가 있으면 켜는 것으로 바꿨다.

붙어 있는 음절은 **간격이 아니라 폭으로 가른다.** 더 작은 간격으로 다시 훑으면
초성·중성 사이 1px 틈에 걸린다. 한 줄 안의 한글 음절 폭은 거의 일정하므로,
혼자 떨어진 덩어리에서 대표 폭을 구하고 붙은 덩어리를 그 폭으로 등분한다.

결과: 두 악보 모두 가사가 정확히 재현된다.
`난 주 곁에 늘 - 거 - 하 리 - 주 님이다스` / `내 마음 다해 - -`

### 빔이 없으면 전부 깃발이 된다

`gendata`(학습 데이터)에는 빔을 넣었지만 `rebuild`(실제 변환)에는 안 넣었다.
위싱 콘티 재조판에서 원본의 빔 묶음이 전부 깃발로 나와서 발견했다. 두 곳이
**같은 함수**(`musicxml.add_beams`)를 쓰게 합쳤다 — 학습 데이터와 변환 결과가
다른 규칙을 쓰면 그림이 어긋난다.

### 음높이 감사 — 개수만 세면 조용히 틀린다

지금까지 "상자 몇 개를 찾았나"만 셌다. 그런데 **개수는 맞고 음이 틀린** 악보가
가장 위험하다 — 연주자가 틀린 걸 모른다. 쉼표가 순서를 밀거나, LLM 음표 순서와
검출 순서가 어긋나거나, 마디 쪼개기가 음표를 잘못 옮기면 그렇게 된다.

`tools/auditpitch.py`가 **키를 바꾸지 않은 판**(`-s 0`)의 XML을 검출 결과와
음표 하나씩 대조한다.

여기서도 감사 도구 자체를 두 번 틀리게 만들었다:

| 시도 | 문제 |
|---|---|
| 그린 결과를 다시 검출해 비교 | 감사 도구의 검출 실패를 오류로 셌다 — 단1에서 XML은 맞는데 5개가 틀린 것처럼 나왔다 |
| 원본 크기에서 검출해 비교 | 재조립은 확대본에서 검출한다. 크기 차이로 생긴 판독 차이가 오류로 잡혔다 (2개) |

**XML을 직접 읽고, 재조립과 같은 확대본에서 검출**하니 답이 나왔다:

```
마커스 「내 마음 다해」  배관 일치 129/129 = 100%  · 못 채운 자리 2개
위싱 콘티 3쪽          배관 일치 197/197 = 100%  · 못 채운 자리 1개
젊은이교회 Setlist 4쪽  배관 일치 204/204 = 100%  · 못 채운 자리 2개
```

**이조 자체도 검사한다.** 0반음 판과 이조한 판을 음표 하나씩 대조해 모두
정확히 (온음계 단수 + 반음)만큼 움직였는지 본다. 이 검사가 없어서 큰 버그를
오래 못 봤다:

```python
n["pitch"] = M.transpose(n["pitch"] + "4", steps, semis)[:-1]   # 틀림
```

음이름에 이미 옥타브가 붙어 있는데 `"4"`를 또 붙여 `"B3"` → `"B34"`
(34옥타브)로 해석됐다. **글자는 맞고 옥타브만 틀려서** 눈으로도 잘 안 보였다
(실측: -3반음에서 D4가 B3 대신 B4). 네 키에서 131개 음표 전부 어긋났다.

웹 경로는 코어의 `transposeNote`를 써서 **처음부터 정확했다**(72건 일치).
CLI만 틀렸다 — 두 경로가 다르면 이런 일이 생긴다. `npm test`가 이제 지킨다.

### 머리글 옮기기 — 송폼이 없으면 콘티를 못 쓴다

첫 단 위에는 제목·부제·작곡자·저작권 표기, 그리고 콘티의 **송폼**이 있다:

```
3. I Thank God Key F
Intro(8) - A1 - A'1 - B - Int(4) - A2 - A'2 - B - Int(8) - Cx4 - Bx2 - Int(8) - B(mute)
```

찬양팀은 이 줄을 보고 연주한다. 다시 조판해서 만들 수 있는 게 아니므로
**픽셀을 그대로 오려 붙인다** — 가사와 같은 이유다. 실측 높이: 마커스 61px ·
위싱 174px · 젊은이교회 174px.

자리를 만드는 게 문제였다. `pageMarginTop`은 **전혀 듣지 않는다**(실측:
0~400 어느 값을 줘도 첫 단 top이 36px 고정 — `breaks="encoded"`에서 무시된다).
그래서 옵션에 기대지 않고 **본문을 그만큼 짧게 그린 뒤 아래로 붙인다.**

그 다음이 까다로웠다:

| 시도 | 결과 |
|---|---|
| 본문 높이를 줄인다 | Verovio는 단을 위에서부터 쌓으므로 압축되지 않는다. 높이가 0이 되어 죽었다 |
| 단 간격을 필요한 만큼 줄인다 | 다음 단 코드가 앞 단 가사와 겹쳤다 |
| **간격은 88%까지만, 남는 건 페이지를 늘린다** | 겹침 없음. 한 페이지 유지 |

페이지가 원본보다 길어질 수 있다(젊은이교회 10단 악보에서 38%). 한 장은
유지되므로 인쇄에는 문제가 없고, **겹치는 것보다 낫다**는 판단이다.

### 구역 표시 — 페이지를 넓혀 넣는다

콘티 악보는 오선 왼쪽 여백에 `A2` · `B` · `C` · `A′` 상자를 둔다. 머리글의
송폼과 짝이 되는 정보라 없으면 곡 형식을 따라갈 수 없다.

위치는 쉽게 찾았다 — 오선이 보통 시작하는 x(단들의 **최빈값**)보다 왼쪽에
잉크가 있는 단이다. 상자의 세로획이 오선으로 잡혀 그 단만 `st.left`가 작아지므로
최빈값을 써야 한다(실측: 젊은이교회 악보에서 보통 83인데 표시가 있는 단만 15·22).

넣는 게 문제였다. `pageMarginLeft` 역시 **전혀 듣지 않는다**(실측: 0~300 어느
값이든 오선 left 가 0). 그대로 원본 자리에 붙이면 음자리표를 덮는다.

해법: **페이지를 표시 폭만큼 넓혀 본문을 오른쪽으로 민다.** 가로 배율은 그대로
여서 가사 x에 오프셋만 더하면 된다 — 가로 배치를 다시 잡는 것보다 안전하다.
실측: 젊은이교회 악보에서 84px(5%) 넓히고 표시 3개를 정확한 자리에 넣었다.

오탐도 막아야 했다. 왼쪽 여백이 좁은 악보(마커스는 `st.left`가 1)에서는 오선
끝 잉크를 표시로 오해해 **없는 표시 9개를 경고했다.** 여백이 3칸 이상이고
잉크 덩어리가 1.2칸 이상일 때만 본다.

### 원조성 — 조표를 세는 게 코드 통계보다 확실하다

**원조성이 틀리면 모든 코드가 틀린다.** 그런데 코드 통계만으로는 갈린다.

실측(위싱 콘티): 코드가 `Bb C F Gm F/A`인데 **Bb키로 추정**했다(확신도 0.13).
실제는 **F키**다 — F=I · Gm=ii · Bb=IV · C=V. 조표는 ♭ 하나로 명확했다.

그래서 **검출기로 조표의 ♯/♭ 개수를 센다**(`evaldet.keysig_counts`).
구간은 음자리표 끝 ~ 첫 음표(또는 박자표) 앞 — 그 밖의 임시표는 곡 중간의
임시표다.

**최빈값이 아니라 "여러 단에서 나온 최대값"을 쓴다.** 조표의 임시표는 붙어
있어서 저해상도에서 하나를 놓치기 쉽고, 놓치는 방향은 늘 "덜 세는" 쪽이다:

| 악보 | 단별 검출 | 최빈값 | **최대값** | 정답 |
|---|---|---|---|---|
| 마커스 | ♭1×6 · ♭2×3 | ♭1 → F ✗ | **♭2 → Bb ✓** | Bb |
| 위싱 콘티 | ♭1×6 · ♭0×3 | ♭1 → F ✓ | **♭1 → F ✓** | F |
| 젊은이교회 | ♭1×10 | ♭1 → F ✓ | **♭1 → F ✓** | F |

거짓 검출 하나로 부풀지 않도록 **2개 단 이상**에서 나온 값만 쓴다.
장·단조는 조표로 갈리지 않으므로 코드로 고른다.

결과: **세 악보 모두 정확**(코드만 쓸 때는 2/3). 브라우저는 서버의 판정을
우선하고, 확신도가 낮으면 "확실하지 않으니 꼭 확인해 주세요"로 바꿔 보여준다.

### 웹의 조표가 늘 C장조로 그려지고 있었다

`plan.fifthsTo ?? 0` — `plan`에는 **`fifthsTo`가 없다.** 파이썬
`render.call_engine`이 따로 넣어 주는 값이라 JS 코어에는 없다. `?? 0`이
말없이 받아 **조표가 늘 C장조(0)로 그려졌다**(F키 -3반음이면 D장조 ♯2여야 한다).

음높이는 맞으므로 소리는 맞고, **조표만 틀린다.** CLI의 옥타브 버그와 같은
종류다 — 눈에 잘 안 보이는 자리에서 틀린다. `fifths(plan.toKey)`로 고쳤고
`npm test`가 8개 조성 조합으로 지킨다.

**두 경로가 갈리면 이런 일이 생긴다.** 이번 세션에 세 번 겪었다:
CLI만 옥타브 버그 · CLI만 조성 기본값 `C` · 웹만 조표 0. 그래서 파이썬↔JS
동등성 테스트를 늘렸다(MusicXML · 빔 · 이조 · 조표).

### 같은 이미지가 RGB와 회색에서 다르게 검출된다

네 번째 악보(여름수련회 DAY2 콘티, 11단)를 `run_all.sh`로 처음부터 돌렸더니
배관 감사가 **95.5%**로 떨어졌다. 한 단에서 6개가 어긋났다.

원인은 악보가 아니라 **입력 모드**였다. 합성 학습 데이터는 회색 PNG인데
(`gendata`가 mode "L"로 저장한다) 호출부마다 RGB를 넣기도, L을 넣기도 했다:

```
같은 확대본 · 같은 모델
RGB 입력 → 머리 199개 · 한 단에서 낮은 점수 후보 5개 받음
L   입력 → 머리 200개 · 한 단에서 낮은 점수 후보 0개 받음
```

그래서 **재조립과 감사가 서로 다른 답을 보고** "배관이 어긋났다"는 잘못된
결론이 나왔다. `evaldet`의 세 함수(`detect_by_staff` · `detect_guided` ·
`keysig_counts`)가 입력을 안에서 회색으로 통일한다 — 호출부를 하나씩 고치는
것보다 확실하다.

고친 뒤 **악보 4종 전부 배관 100%**가 됐다.

### 알 수 없는 것은 어느 단인지 짚어 준다

합계만 알려 주면 사용자가 어디를 봐야 할지 모른다. 그래서 단별로 짚는다:

- **검출 개수 ≠ 판독 개수** — 그 단은 음높이가 밀렸을 수 있다
  (실측: 회색 옵션 음표와 괄호 코드 `(Am7)`가 있는 단에서 검출이 1개 많았다).
  비교 대상은 **LLM이 읽은 음표 수**여야 한다 — 처음엔 "실제로 소비한 머리
  수"와 비교했는데, 그건 검출 수와 같아질 수밖에 없어서 **LLM이 더 많이 읽은
  쪽을 통째로 놓쳤다**(LLM 138개 · 검출 130개인데 경고가 안 났다).
- **화음이 있는 단** — 동시에 울리는 음을 순차 음표로 펴서 그리므로 리듬이
  원본과 다르다. 판정은 **점수가 아니라 개수**로 한다: 실측에서 오검출 쌍은
  (0.82, 0.26), 진짜 화음 쌍은 (0.10, 0.37)·(0.22, 0.30)·(0.69, 0.27)로
  **점수만으로는 안 갈렸다.** 오검출은 한 쌍, 실제 화음 단은 마디마다 쌓여
  여러 쌍이다.
- **박자가 안 맞는 마디** — 다시 읽어도 나아지지 않으면 그대로 두고 알린다

### 조용히 잘리던 아래 단 — `breaks="encoded"`의 함정

젊은이교회 10단 악보 결과에서 **마지막 3단의 오선이 사라지고 가사만 떠 있었다.**

원인: `breaks="encoded"`는 지시받은 단을 **모두 한 페이지에 그린다.** 페이지가
짧아도 2페이지로 나누지 않고 아래로 넘겨 버린다. 그 높이만큼만 래스터화하면
넘친 부분이 잘린다.

```
내용 실제 높이  2,601px
요청한 페이지    2,019px   → 아래 582px 잘림
```

**`getPageCount()`는 1을 반환하므로 경고도 안 뜬다.** 페이지 수만 보고 안심하면
안 된다. 그려진 SVG에서 **오선의 아래끝을 재서** 그만큼 그린다
(`fit_to`가 늘린 높이를 호출부가 받아 써야 한다 — 처음엔 그 값을 버려서
고쳐도 아무 효과가 없었다).

브라우저 경로에도 같은 버그가 있었다. 같은 방법으로 고쳤다.

### 박자가 안 맞는 단만 다시 읽는다 — 검산기를 교정에 쓴다

LLM은 같은 그림에도 매번 조금 다르게 답한다. 실측: 젊은이교회 악보를 두 번
읽었더니 박자 검산이 **41/41과 37/42**로 갈렸다. 나쁜 쪽은 **반복 기호까지 함께
물은** 판이었다 — 한 번에 많이 물으면 음표 읽기가 흐트러진다.

그런데 어느 단이 틀렸는지는 **정답 악보 없이도 안다.** 4/4박이면 마디마다 음가
합이 맞아야 하기 때문이다. 그래서 검산에 걸린 단만 다시 읽고, **나아졌을 때만
바꾼다**(`readstruct.read_page`의 재판독 루프). 나빠지는 쪽으로는 바꾸지 않는다.

첫 마디·마지막 마디의 미달은 눈감아 준다 — 단 경계에서 쪼개진 마디일 수 있다.

### 반복 기호·볼타 — LLM에게 묻는다

콘티는 반복으로 곡을 적는다. 도돌이표(𝄆 𝄇)와 볼타(1./2.)가 없으면 형식을
따라갈 수 없다. 구역 표시와 달리 오선 **안**에 있어 픽셀로 옮길 수 없으므로,
구조 판독에 함께 물어 MusicXML로 다시 그린다:

```xml
<barline location="left">
 <bar-style>heavy-light</bar-style>
 <ending number="1." type="start"/>
 <repeat direction="forward"/>
</barline>
```

마디를 코드 때문에 쪼갠 경우, 반복 기호는 **원래 마디 경계**(첫 조각의 왼쪽,
마지막 조각의 오른쪽)에 붙인다.

### 아직 안 읽는 것

- **D.S. al Coda · 세뇨(𝄋) · 코다(𝄌) · 8va.** 텍스트·기호 표시라 따로 읽어야
  한다.
- **슬러**(구절 이음선). 이음줄(tie)은 LLM이 읽어 재현하지만 슬러는 안 읽는다.
- 가사 음절 경계가 간간이 한 칸 어긋난다(실측: "없- 네"가 "없- 너").
- 재조판 페이지가 원본보다 길어질 수 있다(위 참고).

곁들여 확인된 것: **확대본에서 검출하는 게 더 정확하다.** 오선 간격 6.5px에서
단2·단3·단6이 12·15·15개였는데 18px에서 13·16·16개였다.

`web/musicxml.js` + `web/rebuild.js` + `web/verovio-page.js` + `web/redraw.js`.

## 새 악보로 하는 법

```bash
python3 tools/convert.py 악보.jpg --to G
```

이 한 줄이 전부다. 안에서 네 단계가 돈다.

| 단계 | 방법 | 비용 |
|---|---|---|
| ① 오선·코드 상자 검출 | 영상처리 | 0원 |
| ② 코드 글자 판독 | AI 1회 호출 | **곡당 한 번** |
| ③ 원조성 추론 | 코드의 근음·성질에서 | 0원 |
| ④ 이조 + 렌더 | 브라우저와 같은 코드 | 0원 |

**②는 한 번만 한다.** 결과를 `악보.extraction.json` 으로 옆에 남기므로,
같은 곡을 다섯 키로 뽑아도 AI 비용은 한 번이다. 다시 읽으려면 `--reread`.

### 두 가지 모드

```bash
python3 tools/convert.py 악보.jpg --to G            # 악보 (멜로디 포함)
python3 tools/convert.py 악보.jpg --to G --chart    # 코드차트 (멜로디 없이)
python3 tools/convert.py 악보.jpg -s 2              # 반음 단위로 지정
```

**코드차트에는 틀릴 구석이 구조적으로 없다** — 코드는 텍스트 산술이고 가사는
원본 픽셀이며 오선을 아예 건드리지 않는다. 악보 모드는 음표까지 옮기므로
조표를 다시 그려야 하고, 그게 안 되는 악보가 있다(아래).

### 조표를 못 바꾸면 아무것도 안 옮긴다

조표 위치를 **3단 이상에서 일관되게** 찾지 못하면 음표도 그대로 둔다.
옮겨 놓고 조표를 원본으로 두면 연주자가 원래 조표로 읽었을 때 전부 틀린
음이 되기 때문이다. 그럴 때는 이렇게 알린다:

```
⚠️  조표를 바꾸지 못했습니다 — 조표 검출 1/9단
    조표·음표를 원본 그대로 두었습니다. 코드만 바뀌었으니 …
    → 이 악보는 `--chart` 로 코드차트를 뽑는 편이 정확합니다.
```

실측으로 드러난 실패였다 — 9단 중 1단만 조표를 찾았고 그 위치가 틀렸는데,
그 값으로 9단 전부에 새 조표를 그려 ♯1개짜리 악보가 ♯3개처럼 됐다.
그런데도 "교체 9단 성공"으로 보고했다. **틀린 결과를 성공으로 말하는 것이
가장 나쁘다.**

### 원조성

코드에서 추론한다. 근음뿐 아니라 **성질(장·단)까지** 본다 — 근음만 보면
C장조와 G장조의 온음계 근음이 여섯 개나 겹쳐 구별이 안 된다(실측: G장조
악보를 C장조로 잘못 읽어 악보 전체를 틀리게 이조했다). `D`가 장3화음이면
C장조가 아니다.

확신도가 낮으면 경고한다. 악보의 조표를 보고 다르면 지정하면 된다:

```bash
python3 tools/convert.py 악보.jpg --to G --key Bb
```

### 임시표 경고

변환할 때 멜로디 임시표(♯·♭·♮)를 찾아 몇 단 몇 마디인지 알려준다.
픽셀을 미는 방식은 임시표를 다시 계산하지 못하므로, **어디를 확인해야
하는지** 짚어 주는 것이다. 실제 콘티 22쪽·음표 2,512개에서 멜로디
임시표는 5개(0.2%)였다.

검출기는 별도 환경에 있으므로 경로를 알려줘야 한다:

```bash
MUTE_DETECT_PYTHON=/path/to/venv/bin/python python3 tools/convert.py …
```

없으면 조용히 건너뛴다 — 경고가 없다고 임시표가 없다는 뜻은 아니다.

5. **음원은 서버 전송 0.** SoundTouchJS WASM으로 브라우저에서만.
6. **용어: "편곡" 금지, "키 변환 / 조성 이동"으로 통일.** 마케팅 문구가 법정 증거가 된다.

### 핵심 설계 판단

**1. 반음 수로 이조하지 않는다.** "C에서 2반음 위"는 D일 수도 C##일 수도 있다. 항상 온음계 단계와 반음을 쌍으로 가진 음정을 적용해 올바른 표기를 얻는다. 이 처리를 빼먹으면 `Ebb`, `G##` 같은 악보가 나온다.

**2. 코드 성질 문자열은 해석하지 않는다.** `maj7#11`, `m7b5`, `sus4`, `13(b9)` — 표기 방언이 무한하다. 이조에 필요한 정보는 근음뿐이므로 나머지는 그대로 통과시킨다. 덕분에 처음 보는 표기도 깨지지 않는다.

**3. 근음 직후의 `b`는 항상 임시표.** `Bb9`는 B의 b9이 아니라 B♭의 9다. 변화음(b5·b9·b13)은 성질/숫자 뒤에만 오기 때문에 이 규칙이 안전하다.

**4. 코드로 인식 안 되면 원본 반환.** `N.C.`, `%`, `|`, 가사 등은 손대지 않는다. 코드 트랙 전체에 무조건 적용해도 안전하다.

### 차별화 기능 (원가 0 — 순수 계산)

- **음역 기반 키 추천** — 멜로디 최저·최고음과 부르는 사람 음역으로 최적 키를 계산. "몇 키 내릴까?"를 대신 결정해준다. 판독 단계에서 이미 얻는 데이터라 API 비용이 추가되지 않는다.
- **카포 해법** — 원키 유지하고 카포 위치 + 쉬운 코드 폼 제안. F키 → `카포1+E폼 / 카포3+D폼 / 카포5+C폼`.
- **조표 최소화** — 이명동음 선택 시 임시표가 적은 쪽 자동 선택.

## 🤖 AI 판독 — 조각을 격자로 묶어 한 번에 읽는다

박스 위치는 영상처리가 이미 픽셀 단위로 잡아 놨다. AI는 **글자만** 읽으면 된다.
그리고 박스 43개를 43번 호출하면 비싸고 느리므로, 잘라낸 조각을 확대해
**한 장의 번호 붙은 격자**로 묶어 **1회** 호출한다.

| 항목 | 실측 |
|---|---|
| 조각 수 | 44개 (검출 43 + 오검출 1) |
| 격자 크기 | 2678×1166 → 이미지 토큰 약 **4,163** |
| API 호출 | **1회** |
| 판독 정확도 | **43/43** — 손으로 만든 정답 픽스처와 완전 일치 |
| 오검출 처리 | 음표 조각 1개 → 빈 문자열 반환 → 자동 폐기 |

부수 효과가 크다: 조각은 배경이 거의 없어 **원본 전체를 읽히는 것보다 정확하다.**
그리고 작은 조각을 130px 높이로 확대해 붙이므로 **582px 저해상도 원본에서도 읽힌다.**

번호는 조각 바깥 여백에 **빨간색**으로 넣는다. 악보는 검정이므로 코드 성질의
숫자(7, +5 …)와 혼동될 여지가 없다.

### 실측 원가 · 정확도 (모델 3종 비교)

같은 악보(코드 43개)로 실제 호출해 비교했다.

| 모델 | 입력 | 출력 | USD | 원화/장 | 실제 코드 정확도 |
|---|---|---|---|---|---|
| **Haiku 4.5** | 2,951 | 1,299 | $0.0094 | **13원** | **100% (43/43)** |
| Sonnet 5 | 5,478 | 1,721 | $0.0422 | 58원 | 100% (43/43) |
| Opus 5 | 5,478 | 1,379 | $0.0619 | 85원 | 100% (43/43) |

**모델 급이 결과를 가르지 않았다.** 조각을 130px로 확대해 붙이므로 판독 난도가
낮아진 덕이다. 그래서 기본 모델을 **Haiku 4.5**로 뒀다 (Opus의 1/6.6).

⚠️ 근거는 인쇄 악보 1장이다. 손글씨·저품질 악보로 재검증 전까지
`--model claude-opus-5` 로 되돌릴 수 있게 유지한다.

Haiku 4.5는 `thinking: adaptive`를 지원하지 않아(400) 모델별로 분기한다.
판독은 추론이 거의 필요 없는 작업이라 thinking 없이도 정확도가 같다.

### 코드 여부 판정은 AI가 아니라 파서가 한다

처음엔 모델에게 `is_chord`를 판단시켰다. **틀렸다** — Haiku가 단독 `F`를
"코드 아님"으로 거부해 실제 코드 하나가 사라졌다. 실제 코드를 잃는 건
유령 하나가 더 생기는 것보다 훨씬 비싼 오류다.

그래서 `src/chord.ts`의 파서를 심판으로 세웠다(`cli.ts validate`).
파싱되면 코드다 — 결정론적이고, `F`·`D7+5`는 통과하고 `N.C.`·`%`·`7`·빈칸은 거부한다.

### 남은 경계 사례 1개 — 자동 필터가 아니라 사용자 확인으로

CV 오검출 1개(음표 빔 조각)를 모델이 `Ebmaj7`로 읽는 일이 실행마다 다르게 생긴다
(3회 중 2회). **실제 코드 43개는 매번 정확하고**, 유령은 항상 신뢰도 0.85로
확인 목록에 오른다.

CV 단계에서 없애려고 두 번 시도했고 둘 다 실패했다:
- 박스 높이 필터 → 오검출 24개 → 1개로 줄였지만 마지막 1개는 안 걸림
- "오선에 붙었으면 코드 아님" 판별 → **실제 코드 20개를 잘못 제거** (6px에서는
  코드 아래첨자가 오선에 닿고 기둥·이음줄이 밑을 지나간다)

같은 해상도 벽이다. OCR 제품에서 1/44 경계 사례는 **확인 UI로 넘기는 것이 정답**이다.
잘라낸 조각을 보여주고 "이거 맞나요?" 묻는 편이 자동 판정보다 낫다.

눈으로 보면 놓친다. **모든 키로 변환해 화소 단위로** 검증한다.


|---|---|
| 가사 · 마디선 · 쉼표 · 오선 | 코드 심볼 · 음표 위치(짝수 단) · 조표 |

실제 악보 10개 키 × 데모 악보 10개 키 전부:
**가사 100% · 고정 객체 100% · 오선 잉크 손실 0 · 음표 이동량 정확.**

### 감사가 잡아낸 버그 3개

**1. 코드 심볼이 쉼표로 오분류됐다.** `find_fixed_objects`의 탐색 밴드가 오선 위
2칸까지 걸쳐 `D7+5`의 `D`와 `Fm7`의 `F`가 4·8분쉼표 규격과 일치했다. 그것들을
"고정"으로 취급해 이조해도 안 움직였다 — 코드가 제자리에 얼어붙는 버그다.
→ **덩어리의 세로 중심이 오선 안인지**로 갈랐다. 쉼표·마디선은 오선 안에 있고
코드 심볼은 오선 위에 뜬다. 쉼표 검출 36개 → 24개(오분류 12개 제거).

**2. 멜로디를 안 옮기는 경로에서 오선이 뚫렸다.** 오선 복원이
`if melody["shifted"]` 안에 있어서, 홀수 단 이조에서는 코드 지우기가 낸 구멍이
그대로 남았다(실측: 오선 잉크 16px 소실).
→ 복원을 **이조 방식과 무관하게 항상** 수행하도록 통합했다.

**3. 코드 지우기가 마디선 윗부분을 잘랐다.** 지우기 사각형이 이동량만큼 아래로
확장되어 오선 안까지 들어간다(실측: 마디선 일치율 75~86%).
→ 고정 객체 복원을 **코드 오버레이 뒤로** 옮겼다. 오선 복원과 같은 순서 원칙이다.

### 측정 자체도 틀릴 수 있다

음표 이동량이 6px 기대인데 2.6으로 측정됐다. **마디선·쉼표는 일부러 안 움직이므로
그 열을 측정에서 빼야 한다** — 포함하면 중위값이 0쪽으로 끌려간다.
제외하니 정확히 6.0이 나왔다.

|---|---|
| `이조량 0` | `원키 Bb 그대로입니다.` |
| `온음계 1단은 오선 간격의 정수배가 아닙니다 (3·5·7도만 가능)` | `코드는 C로 바뀌었습니다. 악보의 음표는 원키 그대로이니 왼쪽 코드 진행표를 쓰세요.` |
| `멜로디 8단 +16px 이동 (마디선·쉼표 32개 고정) · 조표 8단 교체` | `악보 전체가 G로 바뀌었습니다 — 코드·멜로디·조표 모두.` |

**무엇이 안 됐는지가 아니라 그래서 무엇을 쓰면 되는지**를 알려준다.
2도 이조에서 음표가 안 움직여도 코드 진행표는 정확하므로, 그걸 쓰라고 안내한다.

### 샘플 악보의 가사를 고쳤다

"가사가 잘 안 들어가는 것 같다"는 지적이 맞았다. 합성 악보의 가사가
**오선 간격의 0.8배**밖에 안 됐다 — 실제 악보는 **1.38배**다. 게다가 왼쪽에
붙어 있고 음표와 정렬되지 않았다.

→ 폰트를 오선 간격의 2.7배로 올리고(음절 높이 1.56배), **음절을 음표 아래에
하나씩** 붙였다. 실제 악보가 그렇게 조판돼 있다.

실제 악보의 가사는 처음부터 100% 그대로였다(이조가 건드리지 않는다) —
문제는 **합성 샘플의 조판**이었다.

## 🌐 공유용 웹 데모 — 왜 데모만 되는가

Artifact 런타임이 페이지에 주는 기능은 `artifact` / `downloads` / `mcp` / `self`
넷뿐이다 — **Claude를 호출하는 기능은 없다.** 그래서 판독 단계를 페이지 안에서
할 수 없다.

그런데 판독 **이후**는 전부 이미 브라우저에서 돈다(이조·멜로디 이동·조표 교체·
코드 오버레이·PDF). 그래서 판독 결과를 미리 구워 넣으면 **공유 가능한 데모**가
된다: 실제 변환 엔진이 실제로 돌아가는 페이지다.

| | 데모 (Artifact) | 실제 앱 (서버 필요) |
|---|---|---|
| 악보 업로드 | ❌ 샘플 고정 | ✅ |
| AI 코드 판독 | ❌ 미리 구움 | ✅ |
| 이조·멜로디·조표·렌더 | ✅ **실제 코드** | ✅ |
| PNG·PDF 내보내기 | ✅ | ✅ |

### 🔴 샘플은 반드시 저작권 없는 악보여야 한다

상용 악보를 공유 페이지에 박는 것은 이 프로젝트가 금지하는 바로 그 행위다
(설계 제약 4번: 공유·유통 금지). 마커스 악보는 Hillsong 저작권물이므로
데모에 쓸 수 없다. `make_test_sheet.py`로 만든 합성 악보를 쓴다 —
A4 세로 비율(1120×1568), 8단, 코드 32개.

부수 효과: 합성 악보는 오선 간격이 16px이라 **조표 교체까지 시연된다.**
저해상도 웹 이미지로는 못 보여주는 부분이다.

### 번들링 — 번들러 없이

Artifact는 외부 호스트 요청이 CSP로 차단되므로 CSS·JS·이미지를 모두
인라인해야 한다. 번들러는 필요 없었다: ESM 모듈의 `import`/`export`만 벗겨
한 스코프에 이어 붙이면 된다(전부 서로 다른 이름을 쓴다). 샘플 악보는
data URI로 넣는다. 최종 **199KB 단일 HTML**.

`--artifact` 플래그를 주면 `<!doctype>/<html>/<head>/<body>`를 뺀다 —
Artifact가 발행 시점에 그 스켈레톤을 감싸주기 때문이다. `body` 클래스를
쓸 수 없으므로 콘텐츠를 `.demo` div로 감싼다.

### 실전에서 걸린 것

**`hidden` 속성이 안 먹었다.** `.btn { display: inline-flex }`가 UA 스타일시트의
`[hidden] { display: none }`을 특이도로 덮는다. 다운로드 기능이 없을 때 버튼을
감추려 했는데 그대로 보였다 — `[hidden] { display: none !important }`를 넣어 고쳤다.

**`claude` 전역은 Artifact 안에만 있다.** 로컬 서버에서 열면
`ReferenceError: claude is not defined`로 페이지가 죽는다. 기능 유무는 `use()`가
null로 알려주지만 전역 자체의 존재는 따로 확인해야 한다.

**음자리표가 코드 밴드를 침범했다.** 합성 악보에 진짜 𝄞 글리프(Apple Symbols에
실제로 있다)를 넣으니 오선 위로 크게 뻗어 단마다 오검출 1개가 생겼다.
실제 악보에도 해당되는 문제라 검출기의 코드 밴드 왼쪽 경계를
오선 간격의 3.2배만큼 밀었다 — 실제 악보 44개는 그대로 유지됐다.

**첫 코드가 headEnd보다 왼쪽에 있었다.** 오선 복원 범위를 headEnd부터로
잡았더니 그 왼쪽 56px에 구멍이 남았다(첫 코드 x=185 < headEnd 240).
머리 구간의 오선은 원본과 동일하므로 **전체 폭**으로 복원하면 안전하다.

## 📄 PDF 내보내기 — 라이브러리 없이

저작권 설계상 결과물은 브라우저에서 만들어져야 하므로 서버 렌더링이나 외부
PDF 서비스를 쓸 수 없다. 라이브러리도 필요 없었다 — 이미지 한 장을 페이지에
앉히는 PDF는 **객체 5개**면 끝난다(카탈로그·Pages·Page·Image·Contents).

**이미지는 JPEG를 그대로 넣는다**(`/DCTDecode`). PDF가 baseline JPEG를 그대로
받아주므로 재압축·색공간 변환이 필요 없다. 무손실 Flate(`CompressionStream`)도
가능하지만 3024×4032 사진이 18MB가 되어 버린다 — 실측 기준으로 JPEG 0.95가
정답이었다(582px 악보 = 185KB).

페이지는 **A4**(595.28×841.89pt)에 비율을 지켜 맞추고 6mm 여백을 둔다.
"입력 N장 = 출력 N장"을 위해 `buildPdf(pages[])`가 여러 장을 받는다.

### 고지 문구는 캔버스로 그린다

출력물에는 `개인 연습용 · 재배포 금지`와 **원본 저작권 표기**가 반드시 들어가야
한다(저작권 설계 6번). 그런데 한글이라 PDF 표준 폰트(Helvetica)로는 못 그린다.
폰트를 임베딩하는 대신 **캔버스에 그려 이미지로 넣는다** — 어차피 페이지 전체가
이미지 한 장이다.

긴 저작권 문구는 **폰트 크기를 줄여** 폭에 맞춘다. `fillText`의 `maxWidth` 인자는
글자를 가로로 찌그러뜨리므로 쓰지 않았다 — 원본 저작권 표기는 읽을 수 있어야
한다(실측: 9px → 7px로 축소, 560/564px에 들어감).

### 검증

바이트 구조를 직접 확인했다: 헤더, 객체 5개의 xref 오프셋이 **모두 실제
`N 0 obj` 위치를 가리킴**, `startxref`가 `xref`를 가리킴, `%%EOF` 종료.
그리고 **macOS PDF 엔진(`qlmanage`)이 정상 렌더**하는 것까지 확인했다 —
바이트가 맞는 것과 리더가 여는 것은 다른 문제다.

## 📷 사진 입력 — 웹 이미지와는 완전히 다른 문제

핸드폰 사진(3024×4032, 화면 촬영본)을 넣어보고 알게 된 것. **웹 이미지용
파이프라인은 사진에서 오선을 하나도 못 찾았다.** 원인이 넷이었다.

| 문제 | 증상 (실측) | 대응 |
|---|---|---|
| 화면 모아레 | 빈 여백 화소가 112~254로 4px 주기 진동 | 저역통과 |
| 종이 질감 | 전역 Otsu 잉크 비율 **38%** (정상 3~12%) | Sauvola 적응형 |
| 기울기 | **+0.75°** → 폭 2400px에서 31px 드리프트 (오선 간격보다 큼) | 투영 프로파일 보정 |
| 초점·조명 기울기 | 단별 선명도 **35 → 9** (아래로 갈수록 흐림) | 사용자에게 경고 |

### 배운 것 1: 국소 '평균' 임계값만으로는 안 된다

평탄한 영역에서 평균보다 어두운 화소는 정의상 절반이다. `gray < mean*0.9`를 걸면
잡음이 대량 통과한다 — 반지름을 15~75px로 바꿔도 잉크 비율이 30~38%에서 안 내려갔다.
**Sauvola**(국소 표준편차 사용)로 바꿔야 평탄한 바탕에서 임계값이 충분히 낮아진다.

### 배운 것 2: 오선 검출 조건이 스캔과 사진에서 다르다

스캔용 조건은 "행의 50% 이상이 잉크"다. 사진은 원근 왜곡 때문에 한 물리적 오선이
여러 행에 번져 그 조건을 못 넘는다(임계값 0.5에서 19개 검출, 0.2에서 47개 — 정답 45개).
그래서 사진 경로는 **긴 가로 런만 남기고**(오선은 길고 질감·음표·가사는 짧다)
채움 임계값을 크게 낮추고, 번져서 갈라진 선을 다시 합친다.

### 배운 것 3: 잉크 비율로 사진/스캔을 가를 수 없다

처음엔 "잉크 20% 넘으면 사진"으로 판정했다가 웹 이미지가 오분류됐다 —
**저해상도 이미지는 표기가 화면을 크게 차지해 잉크 비율이 원래 높다**(582px 이미지에서 21%).
결과로 판단하는 게 맞다: 두 경로를 다 돌려 **오선을 더 많이 찾은 쪽**을 쓴다.

### 배운 것 4: 사진 품질을 사용자에게 알려야 한다

이 사진은 8/9단만 검출됐다. 못 읽은 단은 사진 위·아래 끝이고, 선명도가
중앙 35 대비 9까지 떨어진다. 손으로 들고 찍어 초점·조명이 기울어진 것이다.

**조용히 일부만 처리하면 안 된다.** 단별 선명도를 재서 "어느 부분이 왜 안 됐는지"
알리고 다시 찍게 해야 한다. `tools/prepare.py`가 이 리포트를 낸다.

```
IMG_9688.JPG  3024x4032  [photo]
  · 전역 Otsu 경로: 오선 5단 (간격 26.0px)
  · Sauvola 적응형 이진화 → 잉크 29.2%
  · 기울기 +0.75° 보정
  · 사진 경로: 오선 8단 (간격 26.2px)  → 채택
  단별 선명도: 0:12 1:18 2:30 3:35 4:28 5:18 6:12 7:9
  ⚠️  5개 단이 다른 곳보다 크게 흐립니다 — 정면에서 평평하게 다시 찍어보세요.
```

### 좋은 소식: 해상도는 충분하다

이 사진의 오선 간격은 **26px**로 해상도 게이트(12px)를 크게 넘는다. 즉 사진 입력이면
**조표 교체와 홀수 단 멜로디 이동까지 전부 가능**하다. 전처리만 통과하면 된다.

## ⭐ 저해상도 돌파 — 오선을 제거하지 않는 래스터 이동

**전제:** 사용자는 대부분 웹에서 다운받은 저해상도 이미지를 올린다(500~900px).
스캔·PDF를 요구하는 설계는 대부분의 사용자를 막는다. 그래서 저해상도에서
멜로디를 옮기는 방법이 필요했다.

**착상:** 이동량이 오선 간격의 정수배이면(= 온음계 **짝수** 단) 음표와 오선을
**통째로** 옮겨도 된다. 함께 내려간 오선이 다른 오선 자리에 정확히 내려앉기 때문이다.
그러면 옮겨진 오선 자리만 정리하고 원래 5줄을 되돌리면 끝난다.

**오선을 제거하지 않으므로 음표를 한 번도 건드리지 않는다 → 해상도와 무관하다.**
582px 원본에서 속 빈 2분음표까지 완전히 온전하게 9단 전부 이동됐다.

| | 오선 제거 방식 | 래스터 이동 방식 |
|---|---|---|
| 음표 훼손 | 저해상도에서 속 빈 음표 파괴 | **없음** |
| 최소 해상도 | 오선 간격 12px 이상 | **제한 없음** |
| 적용 범위 | 모든 이조 | 온음계 **짝수** 단 (3도·5도·7도) |

### 한계: 온음계 홀수 단

2도·4도·6도는 이동량이 오선 간격의 **반**이라 옮겨진 선이 칸 가운데에 내려앉는다.
Bb→G(3도, 2단)는 되지만 Bb→C(2도, 1단)는 안 된다. 그 경우는 오선 제거가 필요하고,
따라서 해상도 게이트가 걸린다. 실용적으로 요청의 절반 정도가 짝수 단이다.

### 실전에서 배운 두 함정

**1. 오선 간격은 균일하지 않다.** 이 악보는 6, 6, **7**, 6px였다. 균일하게 6px 옮기니
7px 구간에서 1px 어긋나 선이 겹쳐 두꺼워졌다(실측: 특정 행 잉크 +453px).
개별 보정 대신 일반화했다 — 옮겨진 오선 자리를 **전부** 지우고 원래 5줄을 다시 그린다.

**2. 합성 순서가 중요하다.** 코드를 지우는 사각형이 오선 맨 위 줄을 뚫는다
(실측: 맨 위 줄에서 잉크 118px 소실 → 오선에 구멍). **오선 재작성은 반드시 코드
오버레이 뒤에** 해야 한다. 그리고 순검정으로 칠하면 원본보다 굵어지므로 원본
화소값을 그대로 되돌린다.

### 브라우저 포팅 — CV를 JS로 다시 쓰지 않았다

멜로디 이동과 조표 교체를 브라우저로 옮길 때, Otsu·오선검출까지 JS로 재구현하지
않았다. **서버가 이미 계산한 기하 정보를 구조 데이터로 실어 보낸다:**

```
geometry: { spacing, inkThreshold, staffEditOk,
            systems: [{ staffTop, staffBottom, lineSpans, left, right,
                        thickness, headEnd, keysigRegion }] }
```

브라우저는 이 좌표와 임계값 하나로 픽셀만 옮긴다. 서버는 여전히 좌표와 텍스트만
반환하고 악보 이미지를 만들지 않으므로 저작권 설계도 그대로다.

**실측 검증** (합성 고해상도 1600×688, 오선간격 16px):
`멜로디 3단 +16px 이동 · 조표 3단 교체 — 악보 전체가 변환됐습니다`

저해상도(582px)에서는 멜로디만 이동하고 조표는 게이트에 막힌다고 정확히 보고한다.
멜로디 이동량은 22개 열에서 측정해 **중위값 6px**(= 오선 한 칸, 온음계 2단)로 확인했다.

### 포팅에서 걸린 함정 3개

**1. 캔버스에서 화소마다 getImageData/putImageData 를 부르면 안 된다.**
호출마다 GPU 동기화가 걸려 수만 번 반복하면 사실상 끝나지 않는다(오선이 뭉개진
결과가 나왔다). 캔버스를 **한 번 읽어** 타입 배열에서 전부 처리하고 **한 번 쓴다.**

**2. `lineSpans[-1]`은 맨 아래 줄이다.** y는 아래로 갈수록 커지므로 맨 위 오선은
`[0]`이다. 조표 위치 표(F5=0)가 맨 위 기준이므로 `[0]`을 써야 한다.
파이썬 `keysig.step_to_y`에도 같은 버그가 있었다 — 해상도 게이트에 막혀 드러나지
않고 있었다.

**3. 조표를 지울 범위는 기하학적으로 정해야 한다.** 컴포넌트 분석(`locate`)이
찾은 영역만 지우면 임시표가 남는다(실측: 2개 중 1개만 지워졌다) — 음자리표와
겹치면 놓치기 때문이다. 개수와 글리프 폭은 이미 아니까
"시작점부터 (원래 개수, 새 개수 중 큰 쪽) × 글리프 폭"을 통째로 지운다.

### 쉼표·마디선 고정 — 판별자를 실측으로 정했다

쉼표는 음높이가 없고 마디선은 오선에 정렬돼 있으므로 **둘 다 움직이면 안 된다.**
래스터 이동은 창 전체를 옮기므로 이것들도 따라 내려간다 — 원본 화소로 되돌려야 한다.

추측하지 않고 실제 악보의 컴포넌트 크기 분포를 재서 정했다
(오선 간격 6.5px, 오선 높이 27px):

| 종류 | w/간격 | h/간격 | 채움 |
|---|---|---|---|
| 마디선 | 0.31 | **4.15** (오선 높이) | 1.00 |
| 온·2분쉼표 | 2.31 | **1.23** | **1.00** |
| 4·8분쉼표 | 1.69 | **2.31** | 0.52 |
| 음표+기둥 | 2.2~4.9 | **4.0~5.4** | 0.25~0.50 |

**핵심은 높이다.** 쉼표는 오선 간격의 2.9배 이하, 음표는 기둥 때문에 4배 이상이다.
속 빈 온음표(h/간격 ≈ 0.9)만 온쉼표와 높이가 겹치는데, **채움률**이 다르다 —
쉼표는 꽉 찬 블록(1.0), 음표는 가운데가 비어 0.5다.

원래 자리와 밀려간 자리를 **함께** 되돌린다. 그러지 않으면 밀려간 복사본이
유령으로 남는다.

**검증**: 단0의 마디선 4개·쉼표 5개가 원본과 **화소 100% 일치**,
같은 단의 음표 구간은 35~45% 일치(= 정상적으로 이동됨).
브라우저에서도 동일하게 100% / 51~65%.

### 결과 안내는 세 상태를 구분한다

조용히 일부만 처리하지 않는다.

| 상태 | 문구 |
|---|---|
| 전체 변환 | `멜로디 3단 +16px 이동 · 조표 3단 교체 — 악보 전체가 변환됐습니다` |
| 멜로디까지 | `멜로디 9단 +6px 이동 (마디선·쉼표 68개 고정) — 조표는 원본 키로 남아 있습니다` |
| 코드만 | `코드만 변환됐습니다. 멜로디와 조표는 원본 키로… 코드 차트로 사용해 주세요` |

### 남은 결함 (다음 작업)

- 기둥이 창 경계에서 이동량만큼 짧아진다 (거의 눈에 안 띔).
- 멜로디의 임시표는 조표 변경에 맞춰 다시 계산해야 한다.
- 홀수 단(2·4·6도) 멜로디 이동은 오선 제거가 필요해 해상도 게이트가 걸린다.

## 🔴 해상도 벽 — 오선을 제거해야 하는 작업의 전제조건

조표 교체와 멜로디 이동을 구현하다 **둘 다 같은 벽에 부딪혔다.** 원인이 같아서
한 항목으로 묶는다. 튜닝으로 넘는 문제가 아니다.

두 작업 모두 **오선을 제거**해야 한다. 조표는 오선 안에 있고, 멜로디 이동은 음표만
옮겨야 하므로. 그런데 오선 간격 6px에서는:

| 실패 | 원인 |
|---|---|
| 속 빈 음표(2분·온음표)가 파괴됨 | 음표 테두리가 **1px**. 오선 두께 2~3px와 구별 불가 |
| 음자리표와 조표가 한 덩어리 | 분리할 화소 여유가 없음 → 조표 위치 탐색 실패 |

음표머리 보호 마스크(두꺼운 열 주변을 넓혀 얇은 호를 살림)를 넣어 첫 번째는 해결했지만,
그 대가로 음표 주변에 **오선 조각(stub)이 남는다.** 이걸 같이 옮기면 허공에 뜬 선분이 생긴다.

**결론: 오선 간격 ≥ 12px (긴 변 약 1500px 이상)이 Tier 1.5의 하드 요건이다.**
그 해상도에서는 음표 테두리가 2~3px가 되어 오선과 갈린다.

렌더러에 게이트를 걸었다(`MIN_SPACING_FOR_STAFF_EDIT`). 미달이면 조표·멜로디를 건드리지
않고 이유를 명시한다. **반쯤 망가진 조표를 그리는 것보다 손대지 않고 밝히는 게 낫다.**

용도별로 오선 제거 레이어를 둘로 나눴다:

| 레이어 | 옵션 | 용도 |
|---|---|---|
| 엄격 | `protect_noteheads=False` | 구조가 깨끗히 분리됨. 음자리표·조표·마디선 **위치 탐색** |
| 보호 | `protect_noteheads=True` | 음표 온전. **멜로디 이동** |

### 코드 오버레이(Tier 1)는 이 제한과 무관하다

오선을 전혀 건드리지 않으므로 저해상도에서도 완전히 동작한다. 저해상도 입력은
**"코드 차트"로만 쓸 수 있는 출력**을 내고, 그 사실을 표시한다.

### 멜로디 이동 — 알고리즘은 확정됐다

**이조는 일정한 온음계 간격이므로 모든 음표가 같은 픽셀만큼 세로로 평행이동한다.**
오선에서 온음계 1단 = 오선 간격의 절반. Bb→G는 2단 하강 = 1칸 = 6px.
음표를 하나씩 다시 조판할 필요가 없다.

구현 순서: 오선 제거(보호) → 마디선·음자리표·조표·박자표 제외 → 나머지 N픽셀 이동
→ 오선 다시 그림. 마디선은 오선에 정렬돼 있어 **따라 움직이면 안 된다**(`find_barlines`).

남은 주의점: 오선 밖으로 나가는 음의 덧줄, 멜로디 임시표, 쉼표(음높이가 없으므로
움직이면 안 되는데 분류가 어렵다), 홀수 온음계 단(이동량이 정수 픽셀이 안 됨).

**이게 되면 Tier 2(MusicXML 전체 재조판)가 필요 없어진다.** 마디·페이지 수 보존이
공짜로 따라오고, **AI가 리듬을 판독할 필요도 사라진다** — 지금까지의 실패 원인을 우회한다.

### 표기 정리 (선택)

`F#maj7`을 3반음 내리면 `D#maj7`이 나온다. 음높이는 정확하지만 음악가는 `Ebmaj7`을 쓴다.
엔진은 원본의 표기 관습을 충실히 보존하는데, 조성 밖 반음계 코드에서는 그게 어색해진다.
조성 기준 기능 분석을 붙여 표기를 다듬을 수 있다. 정확성 문제는 아니고 다듬기 항목이다.

## 검증된 설계 판단 — AI에게 좌표를 묻지 않는다

원래 계획은 AI가 코드 텍스트와 좌표를 같이 반환하는 것이었다. 실측하고 바꿨다.

| 역할 | 담당 | 이유 |
|---|---|---|
| 코드 박스 위치 | **고전 영상처리** | 코드 심볼은 오선 위 여백에 뜬 고립된 덩어리라 픽셀 단위로 잡힌다. 비전 모델의 바운딩 박스보다 정확하다 |
| 코드 텍스트 판독 | **AI** | 잘라낸 작은 조각만 읽히면 되므로 싸고 정확하다 |
| 이조 · 렌더 | **브라우저 (결정론적 코드)** | 저작권 설계 + AI에 맡길 이유가 없다 |

판별자도 실측으로 정했다: 박스 **높이**가 코드(12~18px) / 음자리표 갈고리(8~9px) / 빔·잡티(3px)를
깔끔하게 가른다. 그리고 크기 필터는 **병합 뒤에** 걸어야 한다 — 먼저 걸면 `Ebmaj7`의
윗첨자가 개별로는 작아서 버려지고 대문자 E만 남는다.
